## Verdict

Recommendation: **NO-GO** for merge until the major host-evidence scoring bug is fixed and covered by tests.

The PR does add `v_score`, `claimId`, `evidenceMode`, and `sourceCount`, and `delta_score_claim` serializes the full result through `JSON.stringify(result)`. The zero-external mock path still works, peer/dev dependency placement for `@uvrn/score` in `@uvrn/mcp` is correct, and the requested build/test commands pass after dependency setup.

However, the central evidence-score enrichment path can silently score the wrong number whenever a host source title contains a number. That directly undermines the PR's claim that snippet prefixing makes consensus pick up `evidenceScore`.

## Findings

### CRITICAL

None.

### MAJOR

1. `uvrn-mcp/src/tools/handlers.ts:421` and `uvrn-consensus/src/engine/aggregation.ts:57` - `evidenceScore` injection does not reliably control the extracted metric.

What is wrong: The handler maps host sources to FarmSource objects and prefixes only `snippet` with `evidenceScore: N`. The consensus extractor builds content as `${source.title} ${source.snippet}` and returns the first number it finds. Therefore any number in the title wins over the injected evidence score.

Why it matters: Host-provided evidence is the PR's main new path. Real search result titles commonly contain numbers: years, rankings, percentages, prices, release numbers, dates, "Top 10", etc. In those cases `delta_score_claim` can return a finite, apparently canonical `v_score` based on the wrong measurements. This is silent mis-scoring, not a validation failure.

Observed probe against the built PR:

```json
[
  { "label": "Top 10 trend report", "value": 10 },
  { "label": "Source B", "value": 75 }
]
```

The first source had snippet `evidenceScore: 80. Strong demand`, but consensus consumed `10` from the title.

Recommended fix: Do not encode protocol data by string prefixing. Add an additive numeric field to the FarmSource-compatible path, or convert host sources into DataSpecs/normalized numeric sources before consensus. If the short-term workaround must remain, put the evidence score in the title too or change extraction precedence in consensus to parse an explicit `evidenceScore:` token before generic first-number extraction. Add regression tests for numeric titles, numeric snippets, `evidenceScore: 0`, decimals, negatives if allowed, and missing scores.

2. `uvrn-score/src/types/index.ts:34` - `@uvrn/score` redefines the canonical V-Score weights instead of importing them from `@uvrn/core`.

What is wrong: The audit request asked to confirm that `@uvrn/score` does not redefine the V-Score formula. It does export a local `WEIGHTS` constant with `0.35`, `0.35`, and `0.3`, and `ScoreBreakdown` uses that local constant.

Why it matters: The PR's MCP handler does not rederive the formula locally, which is good, but it now depends on `@uvrn/score` as the source of its canonical `v_score`. Under the repo rules, the formula lives only in `@uvrn/core`. Even if today's values match, this creates a second source of truth and a future drift risk.

Recommended fix: Move/export canonical V-Score weights from `@uvrn/core`, then make `@uvrn/score` import them. If `@uvrn/score` is intended to be the canonical formula package, update the house rule and docs explicitly; otherwise this PR should not deepen reliance on a duplicated weight table without fixing the source-of-truth issue.

### MINOR

1. `uvrn-mcp/src/tools/handlers.ts:411` - exactly one host source is silently ignored and connectors/mock are used instead.

What is wrong: The code only enters `host_sources` mode when `input.sources.length >= 2`. With one source, the handler falls through to configured connectors or mock data. This behavior is partly documented in the schema text, but the server does not warn or reject the supplied source.

Why it matters: A caller can believe it is scoring its supplied host evidence while the result is actually `connector` or `mock`. In a configured runtime, the connector is called; in the zero-external path, mock data is used. The result's `evidenceMode` reveals this only after the fact.

Recommended fix: Treat `sources.length === 1` as a `ValidationError` explaining that host evidence requires 2+ sources, or add an explicit `allowFallbackOnInsufficientHostSources` option. At minimum, add a test for one source with connectors configured and one source without connectors.

2. `uvrn-mcp/src/tools/handlers.ts:504` - `sourceCount` reports raw merged sources, not the sources actually scored by consensus.

What is wrong: `sourceCount` is set to `merged.sources.length`. Consensus later parses, drops non-numeric sources, and deduplicates near-identical numeric sources before building components. The returned count can therefore overstate the number of usable/scored sources.

Why it matters: The output field is described as "Number of sources scored", but downstream clients may use it as confidence/provenance metadata. If three sources are supplied and only two parse, or two sources dedupe into one, `sourceCount` does not reflect the scoring basis.

Recommended fix: Return both `rawSourceCount` and `usableSourceCount`, or set `sourceCount` from `consensus.stats.sourceCount` and document that it is the post-parse/post-dedupe count.

3. `uvrn-mcp/src/tools/handlers.ts:534` - derived `claimId` is stable but not collision-safe.

What is wrong: When `input.claimId` is omitted, the handler lowercases the claim and strips non-alphanumeric runs into a slug. Distinct claims can collapse to the same id, for example punctuation-only differences or symbol variants.

Why it matters: The new `claimId` is intended to unblock `delta_compare` chaining. A non-unique derived id can accidentally compare or group unrelated claims if callers omit explicit ids.

Recommended fix: Keep the human-readable slug but append a deterministic short hash of the original claim, or document that callers must provide `claimId` for stable cross-run comparison.

### SUGGESTION

1. `uvrn-mcp/src/__tests__/tools/handlers.test.ts:387` - host-source tests cover the happy path but not the risky paths.

What is wrong: The new test asserts `host_sources`, `claimId`, `sourceCount`, finite `v_score`, and receipt presence, but its titles contain no numbers and its snippets contain no competing numbers. It does not assert the actual extracted values or components.

Why it matters: The current test suite passes while the main evidence-score claim is false for numeric titles. It also misses evidenceScore absent, `0`, decimal, negative/out-of-range, one source, malformed source, and sources plus configured connectors precedence.

Recommended fix: Add tests that inspect the consensus bundle or resulting components, not only finite output shape. Include numeric titles, numeric snippets, `evidenceScore: 0`, missing evidenceScore, one host source, and configured connector precedence.

2. `uvrn-mcp/src/tools/schemas.ts:235` - schema descriptions state intended ranges but do not enforce them.

What is wrong: `credibility` and `evidenceScore` are plain numbers in the JSON schema. The descriptions say `0-1` and `0-100`, but no `minimum`/`maximum` constraints exist.

Why it matters: MCP clients can send out-of-range values that still pass schema shape and then feed consensus unexpected negative or above-100 measurements through the snippet workaround.

Recommended fix: Add `minimum`/`maximum` for both fields. Decide whether negative evidence scores are valid; if not, reject them.

## Requested Checks

- Canonical `v_score`: The handler uses `new ScoreBreakdown(consensus.components, SCORE_PROFILES.general).final`, not `agree.confidence` or a local MCP formula. However, `@uvrn/score` currently has its own local `WEIGHTS`, so the repo-level "formula lives only in core" rule is not satisfied.
- Evidence score injection: Works only when title has no earlier number. It handles `0` because the code checks `!= null`; decimals and negative values match the consensus regex, but there is no range validation. Missing `evidenceScore` falls back to first generic number in title/snippet.
- Precedence: `sources.length >= 2` uses `host_sources`; otherwise configured connectors run; otherwise mock runs. Exactly one host source and `sources: []` do not use host evidence.
- `< 2` merged-sources guard: Raw merged sources fewer than two still throw `ExecutionError` with `nodes` attached. If two raw sources parse/dedupe below two usable consensus sources, the later `ConsensusError` is wrapped as `ExecutionError` without nodes.
- `claimId`: Explicit `input.claimId` is echoed. Omitted ids are deterministic slugs but not collision-safe.
- Server serialization: `uvrn-mcp/src/server.ts:244` returns `JSON.stringify(result, null, 2)`, so the new fields reach clients.

## Design Rule Review

- No storage was added to core/drift/agent.
- `@uvrn/score` is peer + dev dependency in `@uvrn/mcp`; no circular dependency was observed from this PR.
- MasterReceipt structure and core hash integrity are unchanged by this PR.
- Zero-external path remains intact through `DefaultMockConnector`; tests cover `evidenceMode: mock`.
- LLM-friendly output fields on existing receipts are preserved.
- Host evidence is provider-agnostic at the type/import level.
- Design concern: using snippet mutation as a carrier for structured evidence is brittle and should not become the protocol path.

## Known Open Items Assessment

- Deferring an additive `FarmSource.evidenceScore` field is not the right call if host evidence is expected to be reliable. The snippet workaround has already proven vulnerable to title numbers and generic numeric text. It risks silent mis-scoring.
- Low V-Score clustering is expected under the current model when parity measures tight agreement of extracted numeric values. The smell is not that parity is low; the smell is that `evidenceScore` is being treated as the measurement itself through string parsing, while source strength/credibility remains a separate weighting concept.
